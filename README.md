
## Telegram GREEN-API Messenger

Веб-клиент для просмотра списка чатов и истории переписки, а также отправки текстовых сообщений через GREEN-API. Приложение построено на Next.js, React и Redux Toolkit.

## Получение сообщений: почему используется polling

Изначально рассматривался вариант с WebSocket и receive-методами GREEN-API. На практике receive-механика некорректно работала с Telegram, поэтому приложение не полагается на WebSocket и не ожидает push-уведомлений. Получение данных реализовано отдельной изолированной HTTP-логикой: приложение периодически запрашивает историю чатов у GREEN-API и сравнивает последнее сообщение с сохраненным состоянием.

Такой подход проще контролировать и он не блокирует отправку сообщений или загрузку открытой переписки. Обратная сторона polling — обновление не мгновенное: приложение видит новое сообщение при следующем запросе, а частота запросов ограничивается общей очередью и лимитами API.

## Как устроена интеграция

### 1. Подключение инстанса

На экране авторизации пользователь вводит `IdInstance` и `ApiTokenInstance`. Перед открытием чатов приложение:

1. Проверяет состояние инстанса через `getStateInstance`.
2. Продолжает только при статусе `authorized`; для неавторизованного, заблокированного, запускающегося и других неподходящих статусов показывает сообщение об ошибке.
3. Проверяет доступность списка чатов через `getChats`.
4. Сохраняет учетные данные в Redux, после чего отображается интерфейс чатов.

### 2. Первичная загрузка чатов

Хук `useChatsLoader` получает список через `getChats`, а затем для каждого чата:

- загружает профиль личного чата через `getContactInfo`;
- для групп загружает данные через `getGroupData` и отдельно пытается получить аватар через `getAvatar`;
- запрашивает до 10 последних сообщений через `getChatHistory`;
- формирует превью последнего сообщения и сохраняет профиль, историю и список чатов в Redux.

Если профиль или аватар получить не удалось, загрузка списка продолжается с доступными данными. Во время первичной загрузки показывается прогресс.

### 3. Фоновое обновление превью

`useChatLastMessage` работает только после завершения первоначальной загрузки и при наличии учетных данных. Он последовательно проходит по чатам, запрашивает для каждого `getChatHistory` с `count: 1` и сравнивает `idMessage` и `timestamp` с сохраненными значениями. Redux обновляется только при обнаружении нового последнего сообщения.

Между проходами используется таймер с базовым интервалом 500 мс. При ответе `429 Too Many Requests` текущий чат будет повторен, а интервал увеличится вдвое, максимум до 30 секунд. После успешного запроса интервал возвращается к базовому значению.

### 4. Открытая переписка

При выборе чата клиент загружает до 30 сообщений через `getChatHistory`. Кнопка/действие загрузки предыдущих сообщений запрашивает увеличенную выборку (еще 30) и объединяет ее с уже имеющимися сообщениями по `idMessage`, не создавая дубликатов. История открытого чата также перечитывается каждые 30 секунд.

Ответы сортируются по `timestamp` для отображения по времени. Текст превью извлекается общей функцией `getMessageText`, которая используется и в списке, и в переписке.

### 5. Отправка сообщения

Текст отправляется методом `sendMessage` с `chatId` выбранного чата. Запрос ставится в очередь; после успешного ответа с `idMessage` поле ввода очищается и история чата обновляется. Отправку можно запустить кнопкой или клавишей Enter; Shift+Enter не отправляет сообщение.

## Очередь запросов и обработка ошибок

Все вызовы, переданные в `queuedRequest`, выполняются последовательно через общую очередь. Перед вызовом добавляется задержка, соответствующая методу:

| Метод | Минимальная задержка |
| --- | ---: |
| `getChats`, `getChatHistory`, `getContactInfo`, `getGroupData` | 1100 мс |
| `getAvatar` | 150 мс |
| `sendMessage` | 50 мс |
| Остальные методы | 1200 мс |

Очередь снижает вероятность превышения лимитов при первоначальной загрузке и при параллельно активных сценариях. HTTP-ошибки возвращаются `HttpProvider` как объект с `status` и `message`; сетевые исключения обрабатываются вызывающими хуками и компонентами.

## Основные модули

| Файл | Назначение |
| --- | --- |
| `HttpProvider.ts` | GET/POST-запросы и нормализация HTTP-ошибок |
| `utils/api.ts` | Базовый URL GREEN-API |
| `utils/requestQueue.ts` | Последовательная очередь и задержки методов |
| `hooks/useChatsLoader.ts` | Первичная загрузка списка, профилей и короткой истории |
| `hooks/useChatLastMessage.ts` | Изолированный polling последних сообщений для списка чатов |
| `components/Authorization/Authorization.tsx` | Проверка данных и состояния инстанса |
| `components/Chat/Chat.tsx` | История открытого чата и отправка сообщений |
| `store/slices/` | Redux-состояние учетных данных, чатов, профилей и историй |

## Запуск

Требуется установленный Node.js и npm.

```bash
npm install
npm run dev
```

Откройте адрес, который Next.js выведет в терминал (обычно `http://localhost:3000`). Для production-сборки используйте:

```bash
npm run build
npm run start
```

## Настройки и хранение данных

Базовый URL сейчас задан напрямую в `utils/api.ts` (`https://4100.api.green-api.com`). Для работы нужен доступный GREEN-API-инстанс и его `IdInstance`/`ApiTokenInstance`.

Redux Persist сохраняет в `localStorage` браузера учетные данные, список чатов, профили и историю. Кнопка выхода очищает сохраненное состояние. Не используйте приложение с токеном на недоверенном или общем устройстве; для production-сценария с повышенными требованиями к защите учетных данных следует перенести вызовы GREEN-API за серверный proxy и не хранить токен в клиентском хранилище.

В `package.json` настроены команды `dev`, `build` и `start`; отдельная команда автоматических тестов не задана.
